# Continuous integration

*The templates the engine ships, and what they automate.*

The engine's `templates/` directory holds the book-side files a new repository
copies in: a `book.config.json`, a `Justfile`, a compose service for the build
image, a pre-commit config, a link-check config and the workflows. They are the
same shape as the ones in a working book repo, with a few placeholders —
`<owner>`, `<book>` and `<Book Title>` — to replace. The engine's
`templates/README.md` lists each file and what it is for.

## Pre-commit

The pre-commit config does file hygiene — trailing whitespace, end-of-file,
oversized files — and then lints and builds both editions. A commit that would
break the book fails before it lands, on the same checks CI will run.

## Docker

Every build runs in the engine's `docker/` image, which carries Node, LuaLaTeX
and the default fonts. A book copies the compose service and gets a build that
runs the same on any machine:

```sh
just docker-book
```

The image is also what the engine's own CI runs, so a change to the engine is
proven against a real book build before it ships.

## The workflows

Three workflows come with the templates:

- **CI** — lint the engine and the book, then build both editions in Docker and
  keep the website and the PDF as artifacts for a few days.
- **Link check** — visit every external link on a push, a pull request, a weekly
  schedule and on demand, so link rot is noticed without failing the ordinary
  build.
- **Release** — on a `v*` tag, attach the PDF and a zip of the site to the
  GitHub Release.

A book repository holds the Markdown and almost nothing else. The renderers, the
linter, the preview server and the build image all come from the engine, which
the book depends on by path.
